NextCMS

A headless-ish content management system built on Next.js 12, TypeScript and Prisma. Pages are data, not code: content lives in the database and the renderer composes it from a registry of React components.

  • MIT licensed
  • Work in progress
  • Next 12 · React 17
  • PostgreSQL via Prisma

Overview

The repository holds three independent things. It is not an npm workspace — each folder installs and builds on its own.

Part What it is Port
cms/ The public site and the whole HTTP API. Owns the Prisma schema. 3000
admin/ Admin panel on the Metronic theme, served under /admin. Has no database access: it talks to the cms/ API. Still mostly a placeholder. 4000
packages/ The @nextcms/* npm packages — a CLI and scaffolder, CommonJS, independent of the two Next apps. —

The idea worth knowing before reading any code: a page is a row in the Page table plus an ordered list of Component rows. Rendering resolves each block through a static allow-list (cms/components/registry.ts) and loads it with next/dynamic. Nothing is imported from a path stored in the database.

No mail provider is configured. Password recovery creates and validates tokens correctly, but the default transport only logs the message outside production, and in production it drops it. To send real email, implement MailTransport and call setMailTransport — cms/lib/helpers/mailer.ts.

Quick start

Node 24 and a PostgreSQL database. Run everything from inside cms/.

git clone https://github.com/Allan-Nava/NextCMS.git
cd NextCMS/cms
npm ci

cp .env.example .env
# Fill in DATABASE_URL, and generate a secret:
#   openssl rand -base64 48   ->  JWT_SECRET

npx prisma generate      # generate the client
npx prisma db push       # create the tables
npx prisma db seed       # optional: one example page

npm run dev              # http://localhost:3000

The admin panel is a separate install:

cd admin
npm ci
npm run dev              # http://localhost:4000/admin

There is no prisma/migrations directory: this project has always used prisma db push. After changing schema.prisma, push it and re-run prisma generate, otherwise the generated types will not match the code.

Creating the first user

Self-registration is off by default, and user creation is admin-only — which leaves a chicken-and-egg problem on a fresh database. Two ways out: set ALLOW_PUBLIC_REGISTRATION=true, register, then flip isAdmin with npx prisma studio and turn the flag back off; or insert the first admin directly with Prisma Studio (the password column expects a bcrypt hash).

Configuration

Everything is read from the environment. cms/.env.example is the documented list; the table below is the same set with the defaults spelled out.

Variable Required Default What it does
DATABASE_URL yes — PostgreSQL connection string used by Prisma.
JWT_SECRET yes — Signs access and refresh tokens. The app throws if it is missing rather than falling back.
JWT_ACCESS_TTL no 15m Access token lifetime.
JWT_REFRESH_TTL no 7d Refresh token lifetime.
ALLOW_PUBLIC_REGISTRATION no false Opens POST /api/auth/register. It can never create an administrator.
PASSWORD_RESET_TTL_MINUTES no 30 Lifetime of a password reset link.
LOG_LEVEL no info in production, else debug debug | info | warn | error.
BASE_URI no — Public site URL. Used to build password reset links.
API_URI no — Public API URL, exposed to the browser.
ADMIN_URL no — Where the admin app lives.

Architecture

Inside cms/ the layering is strict, and it is the one rule worth respecting when adding code:

  • API routes (pages/api/…) parse the request, apply a guard, validate the payload, and delegate. No SQL, no business rules.
  • Repositories (lib/helpers/*-repo.ts) are the only code that touches Prisma. Password hashing lives here, not in a handler.
  • Helpers — auth.ts (tokens and guards), password-reset.ts, mailer.ts, page-content.ts.
  • Utilities — http.ts (status helpers), validation.ts, rate-limit.ts, logger.ts, env.ts, slug.ts.

Every response uses the same envelope, so a client never has to guess the shape:

{ "response": "OK", "message": "pages retrieved", "data": … }
{ "response": "KO", "error": { "error": "authentication required" } }

Authorisation is enforced in the API handlers, never in _middleware.ts. Middleware runs on the edge runtime, where a JWT signature cannot be verified — so it only checks whether a session cookie exists, to redirect logged-out visitors away from the editor screens.

Data model

Model Purpose
Page A piece of content. type tells pages and posts apart, so they share one slug space and one renderer. Carries SEO fields, an optional category, tags and publishedAt.
Component One block of a page's layout. parent is the page id and position the order within it; template is the registry path.
Category, Tag Taxonomies. A page has at most one category and any number of tags.
User, Role Accounts. isAdmin and isStaff are the flags the guards read.
PasswordResetToken Only the SHA-256 hash of a token is stored. Single use, expiring.
Visit A visit to a page. Not yet recorded by anything.

Deletes are soft everywhere: deletedAt is set and every listing filters on it. Nothing is removed from the database by an API call.

API reference

All routes live under /api. Public needs no token, auth needs a valid access token, admin needs one whose isAdmin claim is true. Send it as Authorization: Bearer <token>, or rely on the access_token cookie the login endpoint sets.

Authentication

Endpoint Access Notes
POST /auth/login public Body {username, password}. Returns {access_token, refresh_token, user} and sets an HttpOnly cookie. 10 attempts per IP per 5 minutes.
POST /auth/logout public Clears the cookie. Tokens are stateless, so a held bearer token must be dropped by the client.
POST /auth/register public 403 unless ALLOW_PUBLIC_REGISTRATION=true. Cannot set role flags. 409 on a duplicate.
GET /auth/me auth The session's user, read from the database rather than from the token claims.
POST /auth/refresh public Body {refresh_token}. Re-reads the user, so a deleted or demoted account stops renewing. An access token presented here is refused.
POST /auth/forgot-password public Always answers 202, so it cannot be used to find out which addresses have accounts.
POST /auth/reset-password public Body {token, password}. The token is single use.

Content

Endpoint Access Notes
GET /page public Filters: ?type=post, ?category=<id>, ?tag=<slug>. An anonymous caller only sees published content; an authenticated one also sees drafts.
POST /page auth Body: title, slug (must start with /), description, optional type, categoryId, tagNames[], published. Unknown tags are created.
GET /page/:id public 404 for a soft-deleted page.
PATCH /page/:id auth Partial update. tagNames replaces the whole tag list.
DELETE /page/:id auth Soft delete.
GET /page/:id/layout public The page's blocks, in order.
PUT /page/:id/layout auth Body {components: [{name, path, props?}]}. Replaces the layout in a transaction. A path that is not in the component registry is rejected.
GET /components public Every stored block. POST creates one (auth).
GET /components/:id public PATCH and DELETE need auth.
GET /category, /tag public List taxonomies. POST creates (auth); the slug is derived from the name when not supplied.
GET /category/:id, /tag/:id public PATCH and DELETE need auth.

Users and roles

Endpoint Access Notes
GET /user admin Never includes the password hash — no endpoint does.
POST /user admin The only way to create a privileged account.
GET /user/:id auth Your own record, or any record if you are an admin.
PATCH /user/:id auth Own record or admin. Only an admin may change isAdmin/isStaff.
DELETE /user/:id admin Hard delete for users.
GET /role, /role/:id admin Full CRUD, admin only.

Authentication

The flow, and the guarantees behind it:

  1. POST /api/auth/login returns an access token (15 min) and a refresh token (7 days).
  2. The access token also arrives as an HttpOnly cookie, so server-rendered pages and the middleware can see that a session exists. JavaScript cannot read it.
  3. POST /api/auth/refresh trades the refresh token for a new pair before expiry.
  4. POST /api/auth/logout clears the cookie.

Properties that are covered by regression tests:

  • A token carries only {sub, username, isAdmin, isStaff} — never the user row, never a hash.
  • A tampered or foreign-signed token is refused.
  • A refresh token cannot be used as an access token, and the reverse is also false.
  • A missing JWT_SECRET throws instead of falling back to a default.

Rate limit counters live in the process memory. Behind more than one instance the effective limit is per instance; a shared store is the next step if the app is scaled out.

Content and the page builder

Pages and posts are the same table, told apart by type. The editor screens live in the cms app and sit behind the session middleware:

Screen What it does
/content List everything, filter by type, jump to the editor or the layout, delete.
/content/new, /content/:id Create and edit: title, slug, description, type, category, tags, SEO fields, published flag.
/page-builder?page=:id Drag blocks from the palette, reorder or remove them, then save.
/profile Your own account: email, name, password.

The builder's palette is the component registry, not the database — those are the components the renderer can actually draw. Adding one is a single line in cms/components/registry.ts next to a real import(), which is what lets webpack resolve it statically: 

export const COMPONENT_REGISTRY: Record<string, ComponentType<any>> = {
  './Elements/Navbar': dynamic(() => import('./Elements/Navbar')),
  './Elements/Hero': dynamic(() => import('./Elements/Hero')),
  // add yours here
};

Saving a layout replaces it: the previous blocks are soft-deleted and the new ones inserted with their position, inside a transaction — a half-written layout would render a mixture of two versions.

Not built yet: per-block settings in the UI (props are stored but not editable), image and media handling, and nested blocks (the data model supports them, the editor does not).

Deploying

Vercel

The repository root is not a deployable application: it has no next dependency and no build script. Each app deploys as its own Vercel project, and the setting that makes this work lives in the dashboard rather than in git.

Setting Value for the public site Value for the admin panel
Root Directory cms admin
Framework preset Next.js (also pinned in cms/vercel.json) Next.js
Node version from engines.node (24.x) from engines.node (24.x)
Required environment variables DATABASE_URL, JWT_SECRET —

Root Directory must be set to cms (or admin). Vercel cannot infer it, and vercel.json cannot express it for a Next.js app in a subdirectory. With it left at the repository root the build fails before it starts: there is nothing there to build.

engines.node in each app's package.json takes precedence over the dashboard's Node version, so the deployed runtime is declared in git rather than living as invisible project state.

Why the build command runs prisma generate

The generated Prisma client lives in node_modules/.prisma. Vercel restores node_modules from its build cache, which means the @prisma/client postinstall — the thing that normally generates the client — does not run on a cached build. The client is then missing and the build fails while type-checking, with Module '"@prisma/client"' has no exported member 'Prisma'.

So the build script generates it explicitly, and must keep doing so: 

"build": "next telemetry disable && prisma generate && next build"

prisma generate does not need a reachable database, or even DATABASE_URL, so this is safe at build time.

Docker

cms/Dockerfile is the maintained image and is published to ghcr.io by the docker-publish workflow on every tag. The root Dockerfile and Dockerfile-slim do not build anything — same reason as above — and are tracked for removal.

Database migrations

There is no prisma/migrations directory: schema changes are applied with prisma db push. Nothing in the deploy pipeline does this for you, so a release that changes the schema needs the push run against the target database before the new code serves traffic.

How work is tracked

Three rules, and they are enforced by tooling rather than by good intentions:

  • Every task is an item. BACKLOG.md is the single source of truth, with stable NC-n ids that are never reused or renumbered. A push that touches it syncs the items to GitHub issues and the sections to milestones, so ticking an item in the file closes its issue.
  • Every feature is a tagged release with its own CHANGELOG.md section, including what was verified and what was not.
  • Documentation ships with the change. A change to the architecture, the env vars, the schema or an API contract updates the docs in the same commit.

npm packages

The @nextcms/* packages cannot currently be installed. @nextcms/nextcms@0.1.19 depends on sibling versions that were never published to npm (@nextcms/generators@0.1.4, @nextcms/utils@0.1.10), so npm install fails with notarget. Fixing it means either publishing the missing versions or resolving the siblings locally through npm workspaces. Tracked as NC-51.

The packages themselves are a Strapi-inspired CLI and scaffolder on Koa, independent of the two Next apps in this repository.
